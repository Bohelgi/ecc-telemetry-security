# ecc-telemetry-security

## Анотація

Програмний прототип криптографічного захисту телеметричних даних для
Smart Energy Lab, реалізований мовою C++17. Забезпечує конфіденційність,
цілісність та автентичність телеметрії, а також стійкість до повторного
відтворення повідомлень (replay-атак), на основі криптографії на
еліптичних кривих (ECC): узгодження сеансового ключа за схемою
Diffie-Hellman на кривій NIST P-256 (ECDH), симетричне шифрування
AES-256-GCM та цифровий підпис ECDSA-SHA256. Рішення відповідає
завданням магістерської дисертації («Розробка та впровадження
криптографічних механізмів захисту телеметричних даних у Smart Energy
Lab»), замінюючи спочатку заплановане RSA-рішення на ECC — обґрунтування
наведено в розділі 3.9.

---

# 1. Вступ і постановка задачі

Телеметричні дані енергетичних систем (напруга, струм, потужність,
температура), що передаються від кінцевих вузлів (лічильники, давачі,
контролери) до центрального шлюзу/бекенду, за відсутності криптографічного
захисту вразливі до пасивного перехоплення, активної підміни даних та
видавання себе за легітимний пристрій. Мета роботи — розробити, програмно
реалізувати та експериментально перевірити мінімальний, але коректний
криптографічний протокол, що усуває ці загрози, з урахуванням ресурсних
обмежень вузлів (потенційне цільове середовище виконання — мікроконтролер
ESP32).

# 2. Модель загроз

Розглядається зловмисник, що контролює канал передавання даних між
пристроєм і шлюзом (модель Dolev-Yao: може прослуховувати, затримувати,
видаляти, модифікувати та повторно надсилати будь-які повідомлення), але
не має доступу до приватних ключів легітимних учасників протоколу.

| № | Клас атаки | Опис | Механізм протидії |
|---|---|---|---|
| 1 | Пасивне прослуховування | Зловмисник читає вміст переданих пакетів | AES-256-GCM (розділ 3.3) |
| 2 | Активна підміна даних (MITM) | Зловмисник змінює байти пакета в польоті | Тег AES-GCM + ECDSA-підпис конверта (3.3, 3.4) |
| 3 | Повторне відтворення (replay) | Зловмисник записує й повторно надсилає легітимний пакет | Монотонний лічильник послідовності (3.5) |
| 4 | Підробка відправника | Зловмисник підписує пакет власним ключем, видаючи за чужий `deviceId` | Перевірка підпису саме проти зареєстрованого ключа (3.4) |
| 5 | Підключення незареєстрованого пристрою | Стороннiй, криптографічно коректний пристрій намагається пройти хендшейк | Білий список `deviceId` на шлюзі (розділ 4) |

Поза межами моделі загроз (свідомі спрощення — розділ 5): компрометація
самого пристрою чи шлюзу (крадіжка довгострокового приватного ключа),
DoS-атаки на мережевому рівні, атаки на генератор випадкових чисел.

# 3. Криптографічний механізм

### 3.1 Довгострокова ідентичність пристрою

Кожен пристрій має постійну пару ключів ECDSA на кривій **NIST P-256**
(secp256r1, FIPS 186-4): приватний ключ — 256-бітний скаляр (32 байти),
публічний ключ — точка кривої в нестисненому форматі (1 байт тегу `0x04`
+ 2×32 байти координат = 65 байт). Ця пара є довготривалою автентичністю
пристрою (аналог "особистого підпису") і не змінюється між сеансами
зв'язку; реалізація — клас `EccIdentity` (`crypto_primitives.hpp/.cpp`).
Публічний ключ кожного довіреного пристрою заздалегідь заноситься в
реєстр шлюзу (`GatewayAgent::registerTrustedDevice`, провіжнінг).

### 3.2 Узгодження сеансового ключа (ECDH + HKDF-SHA256)

На початку кожного сеансу зв'язку пристрій і шлюз виконують хендшейк:

1. Обидві сторони генерують одноразову (ефемерну) пару ключів ECDH на
   тій самій кривій P-256 (`EphemeralKeyPair`).
2. Пристрій надсилає `Hello(deviceId, Q_A)`, шлюз відповідає
   `Hello(Q_B)`, де `Q_A`, `Q_B` — публічні ефемерні ключі.
3. Кожна сторона обчислює спільний секрет `Z = x(d_A · Q_B) = x(d_B · Q_A)`
   (стандартна властивість ECDH; `d` — приватний скаляр, `Q` — публічна
   точка, `x(·)` — x-координата результату).
4. Сесійний ключ виводиться через **HKDF-SHA256** (RFC 5869):

   `K_session = HKDF-SHA256(salt = transcript, IKM = Z, info = "secure-telemetry-v1", L = 32)`

   де `transcript = deviceId ‖ Q_A ‖ Q_B` — прив'язка виведеного ключа до
   конкретного хендшейку (запобігає плутанині ключів між паралельними
   сесіями), `info` — фіксований контекстний рядок протоколу.

Результат — 256-бітний симетричний ключ AES. Ефемерні приватні ключі
`d_A`, `d_B` після обчислення `Z` ніде не зберігаються — це забезпечує
**пряму секретність (forward secrecy)**: компрометація довгострокового
ключа ідентичності в майбутньому не дає змоги розшифрувати раніше
перехоплений трафік минулих сесій, оскільки відповідні ефемерні ключі
безповоротно втрачені.

### 3.3 Конфіденційність і цілісність даних (AES-256-GCM)

Кожен пакет телеметрії `P` (серіалізований `TelemetryPacket`, 24 байти:
мітка часу `u64` + 4 значення `float`) шифрується сесійним ключем:

`(C, T) = AES-256-GCM-Encrypt(K_session, N, AAD, P)`

- `N` — 96-бітний (12-байтовий) nonce, генерується криптографічно стійким
  ГВЧ (`RandomSource`, CTR_DRBG) окремо для кожного повідомлення;
- `AAD = deviceId ‖ seq` (додаткові автентифіковані дані — не шифруються,
  але входять у обчислення тегу, зв'язуючи шифротекст із конкретним
  відправником і номером послідовності);
- `T` — 128-бітний (16-байтовий) тег автентичності GCM;
- `C` — шифротекст (`AesGcmCipher`, `crypto_primitives.hpp/.cpp`).

Розшифрування (`AES-256-GCM-Decrypt`) на боці шлюзу з тим самим `K_session`,
`N`, `AAD` повертає `P` лише за умови, що `T` збігається обчислено —
будь-яка зміна `C`, `N` або `AAD` після шифрування призводить до
розбіжності тега й відхилення повідомлення (`SecurityException`).

### 3.4 Автентичність повідомлення (цифровий підпис конверта)

Кожне надіслане повідомлення (`TelemetryEnvelope`) додатково підписується
довгостроковим ключем ідентичності пристрою (не сесійним!) за схемою
**ECDSA-SHA256**:

`σ = ECDSA-Sign(d_identity, SHA-256(deviceId ‖ seq ‖ N ‖ C ‖ T))`

Підпис (`TelemetryEnvelope::signedTranscript()`) охоплює *весь* конверт,
включно з уже зашифрованими `C` і `T` — тому підміна шифротексту "в
польоті" ламає одразу й підпис, а не лише тег GCM. Підпис кодується в
форматі DER (ASN.1), фактична довжина варіюється — на кривій P-256
типово 70-72 байти. Шлюз перевіряє підпис функцією
`EccIdentity::verify()` проти публічного ключа, зареєстрованого саме за
цим `deviceId` (розділ 3.1) — тобто автентифікується не факт "якийсь
валідний підпис існує", а належність підпису конкретному заявленому
відправнику.

### 3.5 Захист від повторного відтворення (anti-replay)

Кожне повідомлення несе монотонно зростаючий 32-бітний номер послідовності
`seq`. Шлюз зберігає для кожного активного сеансу останній прийнятий
номер `lastSeq[deviceId]` і приймає повідомлення лише за умови
`seq > lastSeq[deviceId]`, після чого оновлює `lastSeq[deviceId] := seq`
(`GatewayAgent::unprotect`). Умова — строге зростання, а не рівність
`lastSeq + 1`: протокол коректно приймає пропуски в нумерації (втрата
пакетів мережею — штатна ситуація), але відхиляє будь-який номер, що не
перевищує вже прийнятий, незалежно від того, чи це точний дублікат, чи
просто застарілий пакет.

### 3.6 Формат серіалізації даних (wire format)

Внутрішній бінарний формат (`wire::Writer`/`wire::Reader`, `support.hpp/.cpp`) —
послідовність полів фіксованого розміру (`u8`, `u32` — 4 байти
big-endian, `u64` — 8 байтів big-endian, `float` — 4 байти в порядку
байтів хост-системи) та змінної довжини (масиви байтів і рядки — префікс
довжини `u16` big-endian + вміст, максимум 65535 байт на поле). Формат
симетричний для серіалізації/десеріалізації, покривається тестом
`testWireFormat` (розділ 6). Оскільки `float` серіалізується без
перетворення порядку байтів, коректний міжплатформний обмін передбачає
однаковий порядок байтів на обох кінцях (little-endian) — виконується
для типової пари ESP32/x86-64-сервер; це задокументоване припущення, не
проблема на практиці для цільової конфігурації.

### 3.7 Послідовність кроків протоколу

```
Пристрій (довгостроковий ключ ECDSA)                Шлюз (реєстр довірених ключів)
   |                                                    |
   |------------------- Hello(deviceId, Q_A) ---------->|  1. ECDH-хендшейк: генерація
   |<------------------ Hello(Q_B) ----------------------|     ефемерних пар, обчислення
   |                                                    |     Z, виведення K_session
   |   Z = ECDH(d_A, Q_B) = ECDH(d_B, Q_A)               |     через HKDF-SHA256
   |   K_session = HKDF-SHA256(Z; transcript)            |
   |                                                    |
   |-- TelemetryEnvelope: --------------------------->|  2. На кожен пакет:
   |     deviceId, seq, N,                              |     AES-256-GCM(K_session, ...),
   |     C = AES-256-GCM(K_session, N, AAD, P),          |     ECDSA-підпис довгостроковим
   |     T, σ = ECDSA-Sign(d_identity, ...)              |     ключем ідентичності
   |                                                    |
   |                                                    |  3. Шлюз: isTrusted(deviceId) ->
   |                                                    |     verify(σ) -> seq > lastSeq ->
   |                                                    |     AES-GCM-Decrypt (перевірка T)
```

### 3.8 Зведена таблиця властивостей

| Властивість | Механізм |
|---|---|
| Конфіденційність | AES-256-GCM із сесійним ключем, отриманим через ECDH (P-256) |
| Цілісність повідомлення | Тег автентифікації AES-GCM (над `AAD = deviceId ‖ seq` і шифротекстом) |
| Автентичність/непідробність | Цифровий підпис ECDSA-SHA256 довгостроковим ключем пристрою |
| Стійкість до replay | Монотонний лічильник послідовності, перевірений шлюзом |
| Пряма секретність (forward secrecy) | Ефемерні ECDH-ключі генеруються на сесію й ніде не зберігаються |

### 3.9 Обґрунтування вибору ECC замість RSA

Вихідне формулювання теми диплому передбачало RSA; за погодженням з
керівником використано ECC (ECDH/ECDSA на P-256). Порівняння за розміром
ключів і підписів для еквівалентного рівня безпеки (~128 біт симетричного
еквівалента, NIST SP 800-57):

| Параметр | ECC (P-256) | RSA-3072 |
|---|---|---|
| Приватний ключ | 32 байти | 384 байти (модуль) |
| Публічний ключ (нестиснений/DER) | 65 байт | ≈398 байт |
| Підпис | ≈70-72 байти (DER, змінна довжина) | 384 байти (фіксовано) |

Менший розмір ключів і підписів прямо зменшує обсяг службових даних на
кожен пакет телеметрії та витрати пам'яті на зберігання ключів — істотно
для вузлів з обмеженими ресурсами (ESP32), що відповідає завданню
дослідження "визначити обмеження… з урахуванням специфіки телеметричних
даних (обсяг, швидкість, ресурсні обмеження)". Обчислювальна перевага
ECC над RSA-3072 на операціях підпису/перевірки є загальновідомим фактом
(менша розрядність арифметики), проте систематичне емпіричне вимірювання
продуктивності (час хендшейку, шифрування/підпису одного пакета) в
поточній версії роботи не проведено.

# 5. Усвідомлені спрощення та обмеження

- **Шлюз не автентифікує себе перед пристроєм на етапі хендшейку.**
  Пристрій не перевіряє, що ефемерний ключ у відповіді `Hello` належить
  легітимному шлюзу — залишається можливою MITM-атака саме на цьому
  кроці. Прийнятне спрощення в межах поточного етапу (основна модель
  загроз орієнтована на підробку/підміну даних від вузла, а не від
  колектора); напрям подальшої роботи — опінований (pinned) публічний
  ключ шлюзу або взаємна автентифікація (mutual ECDSA).
- **Лічильник послідовності не персистентний** — обнуляється при
  перезапуску `device_simulator`. На реальному ESP32 потребує збереження
  в енергонезалежній пам'яті (NVS), інакше перезапуск пристрою відкриває
  вікно для replay-атаки в межах уже прийнятих номерів.
- **`gateway_verifier` обробляє TCP-з'єднання послідовно, одне за раз**
  (прийнятно для демонстрації; для промислового навантаження — потік або
  асинхронний обробник на пристрій, без зміни логіки `GatewayAgent`; HTTP-
  транспорт уже багатопотоковий).
- **Продуктивність не виміряна емпірично** (розділ 3.9, 10).

`crypto_tests.exe`, `security_demo.exe`.

# 8. Демонстраційні сценарії

### 8.1 Базовий запуск (два застосунки по TCP)

```powershell
./build/Release/crypto_tests.exe

./build/Release/device_simulator.exe --id esp32-node-01 --export-identity trust_store.txt
./build/Release/gateway_verifier.exe --port 9443 --trust-store trust_store.txt
./build/Release/device_simulator.exe --id esp32-node-01 --port 9443 --interval 2000
```

Вебдашборд доступний на `http://localhost:<http-port>` одразу після
старту `gateway_verifier` (типово `--http-port 8090`): `/` — версія на
JS/Chart.js, `/react-preview.html` — попередній перегляд React-версії
(`web/Dashboard.jsx`).

### 8.2 Демонстрація відхилення атаки

`device_simulator` приймає прапорець
`--attack none|tamper|replay|both|forge|unknown` (типово `none`) — вмикає
відповідний сценарій атаки без перезбирання:

| Значення | Яку атаку з розділу 2 демонструє | Де відхиляється |
|---|---|---|
| `tamper` | 2 — підміна шифротексту в польоті | Перевірка ECDSA-підпису (`unprotect`) |
| `replay` | 3 — повторне відтворення | Перевірка номера послідовності (`unprotect`) |
| `both` | 2 і 3 одночасно | — |
| `forge` | 4 — підробка відправника (підпис чужим ключем) | Перевірка ECDSA-підпису проти зареєстрованого ключа (`unprotect`) |
| `unknown` | 5 — підключення незареєстрованого пристрою | Перевірка білого списку ще на хендшейку (`acceptHello`) |

```powershell
./build/Release/device_simulator.exe --id esp32-node-01 --port 9443 --attack both
./build/Release/device_simulator.exe --id esp32-node-01 --port 9443 --attack forge
./build/Release/device_simulator.exe --id esp32-node-01 --port 9443 --attack unknown
```

Для `forge`/`tamper`/`replay`/`both` шлюз і дашборд позначають окремі
пакети як `REJECTED` із точною причиною, решта потоку триває штатно. Для
`unknown` відхиляється вже сам хендшейк — сесія не встановлюється
взагалі, програма завершується одразу після підтвердження відхилення.

### 8.4 Демонстрація на розгорнутому сервері (додатково)

Розділи 8.1-8.3 — основний, самодостатній спосіб перевірки: локальний
`gateway_verifier` + `device_simulator`, нічого стороннього не потребує.

команди Smart Energy Lab (Docker-образ `olehmedvediev/ecc-telemetry-security`,
інтегрований у `rozumnaEnergia` через `docker-compose.yaml`), і всі ті самі
сценарії можна відтворити наживо проти нього — з тим самим `.exe`, без
перезбирання, просто вказавши `--host`:

- Вебдашборд: **http://77.47.192.6:5173/telemetry-security-medvediev**
- Пристрій `esp32-medvediev-live` вже зареєстрований у довіреному списку
  шлюзу на сервері.

```powershell
# штатна робота
./build/Release/device_simulator.exe --id esp32-medvediev-live --host 77.47.192.6 --port 6020 --transport http --interval 2000

# атаки, по одній
./build/Release/device_simulator.exe --id esp32-medvediev-live --host 77.47.192.6 --port 6020 --transport http --attack tamper
./build/Release/device_simulator.exe --id esp32-medvediev-live --host 77.47.192.6 --port 6020 --transport http --attack replay
./build/Release/device_simulator.exe --id esp32-medvediev-live --host 77.47.192.6 --port 6020 --transport http --attack forge
./build/Release/device_simulator.exe --id esp32-medvediev-live --host 77.47.192.6 --port 6020 --transport http --attack unknown

```

Це той самий протокол і той самий код, що й у 8.1-8.3 — тож результат
(`ПРИЙНЯТО`/`ВІДХИЛЕНО` на дашборді, ідентичні причини відхилення)
підтверджує не лише коректність криптографії саму собою, а й те, що вона
працює без змін у реальному розгорнутому середовищі, а не лише
"на localhost".

```powershell
./build/Release/device_simulator.exe --id esp32-node-01 --port 8090 --transport http
```
